Firestore Database

Last session, people could log in. Now their data goes to the cloud: it belongs to their account, appears on every device they use, and updates live the moment it changes. Then you'll lock it down so nobody can read anyone else's data.

By the end of today you can

Create, read, update and delete documents in Firestore, show them live with a Stream, store data per user with a userId field, and write security rules so users can only see their own data.

The big picture: a filing cabinet in the cloud

Firestore is Firebase's database. It isn't a table like Excel; it's a filing cabinet. Each drawer is a collection. Inside each drawer are documents, each one like a single sheet of paper with labelled boxes (fields) on it. Every sheet has a unique id.

collection: notes
id: a8Fk2Lq…title: "Revise Riverpod"body: "watch vs read"userId: "u7Hs…"createdAt: 16 Oct, 10:42
id: Zp91mXc…title: "Buy milk"body: ""userId: "k2Qa…"createdAt: 16 Oct, 11:05
collection: shoppingItems
id: 3Jd8sWq…name: "Rice 5 kg"done: falseuserId: "u7Hs…"

Two more ideas make Firestore special:

  • It's live. When a document changes, every phone and browser that is watching sees the change within a second, like a shared Google Doc.
  • It has a security guard. Security rules check the ID badge from Session 8 before letting anyone read or write. Without rules, anyone could read everything.

Setup

  1. Firebase console → Build → Firestore Database → Create database. Pick a location close to your users (e.g. asia-south1, Mumbai), then Start in production mode. We'll write our own rules today.
  2. Add the package: flutter pub add cloud_firestore
  3. Keep everything from Session 8: Firebase.initializeApp in main(), and the auth gate. Firestore data belongs to the logged-in user.

2

A model class for documents

Same idea as Session 6's fromJson: read the document once, in one place. The document's id isn't inside its fields, so we pass it in separately.

class Note {
  const Note({required this.id, required this.title, required this.body, this.createdAt});
  final String id;
  final String title;
  final String body;
  final DateTime? createdAt;

  factory Note.fromFirestore(DocumentSnapshot<Map<String, dynamic>> doc) {
    final data = doc.data()!;
    return Note(
      id: doc.id,                                              // the id comes from the document
      title: data['title'] as String,
      body: data['body'] as String? ?? '',
      createdAt: (data['createdAt'] as Timestamp?)?.toDate(),   // can be null for a moment, see below
    );
  }
}
Why createdAt can be null

When you add a note, Firestore shows it on your screen straight away, before the server has stamped its time. For that first moment createdAt is null. A second later the real time arrives and the stream sends the note again. Always make the time nullable (Timestamp?) and show “Just now” when it's null.

3

Live updates: StreamBuilder and StreamProvider

.snapshots() is a Stream: it sends the whole list again whenever anything changes, on any device. Show it with a StreamBuilder (the Flutter way) or a StreamProvider (the Riverpod way, like Session 8's auth gate).

// Only MY notes, newest first
final myNotesProvider = StreamProvider<List<Note>>((ref) {
  final uid = ref.watch(authStateProvider).value?.uid;     // from Session 8
  if (uid == null) return Stream.value([]);                // logged out → no notes

  return FirebaseFirestore.instance
      .collection('notes')
      .where('userId', isEqualTo: uid)
      .orderBy('createdAt', descending: true)
      .snapshots()
      .map((snapshot) => snapshot.docs.map(Note.fromFirestore).toList());
});

// In a ConsumerWidget, exactly like Session 6:
ref.watch(myNotesProvider).when(
  loading: () => Spinner(),
  error: (e, _) => ErrorView(e),
  data: (notes) => notes.isEmpty ? EmptyState() : NotesList(notes),
);

Try this in class: open the app in two windows (or on a phone and in Chrome), logged in as the same user. Add a note in one, and it appears in the other within a second. Open the Firebase console's Data tab too: it updates live as well.

The index error (everyone gets this once)

A query that filters on one field (userId) and sorts by another (createdAt) needs an index. The first time, the app shows an error saying “The query requires an index” with a link. Open the link, click Create index, and wait a minute or two. The query then works.

5

Security rules: users only see their own data

The Flutter code filters by userId, but that only protects honest apps. Someone could write their own code and ask for everyone's notes. Rules run on Firebase's servers, so they can't be skipped.

When you create the database you choose one of two starting points, and neither is safe for a real app:

ModeDefault ruleProblem
Test modeallow read, write: if request.time < …30 days…;Open: anyone on the internet can read and change everything, for 30 days
Production modeallow read, write: if false;Locked: nobody can read or write anything, including your own app

Write rules that say exactly who may do what. Firebase console → Firestore → Rules → paste → Publish:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /notes/{noteId} {
      // Read, change or delete a note only if it's yours
      allow read, update, delete: if request.auth != null
                                 && request.auth.uid == resource.data.userId;
      // Create a note only with YOUR id in it
      allow create: if request.auth != null
                    && request.auth.uid == request.resource.data.userId;
    }
  }
}
In the ruleMeans
request.authThe badge of whoever is asking. null = not logged in
request.auth.uidTheir user id (Session 8's user.uid)
resource.dataThe document as it is now in the database
request.resource.dataThe document as it would be after this write (used when creating)
Rules are not filters

If your query asks for all notes, Firebase refuses the whole query with permission-denied, even though some of them are yours. The query must ask only for what the rules allow: always include .where('userId', isEqualTo: uid).

Prove it works: register two accounts. Add notes as User A. Log out, log in as User B: B sees none of A's notes. Then try a query without the where and watch it fail with permission-denied.

Check yourself

What's the difference between a collection and a document?

A collection is a drawer that holds many documents. A document is one record with an id and fields.

What's the difference between .get() and .snapshots()?

.get() reads once. .snapshots() is a Stream that sends the data again every time it changes.

Why do we store userId in every document?

So we can ask only for the current user's documents, and so the security rules can check that a document belongs to whoever is asking.

Why isn't filtering by userId in Flutter enough to keep data private?

Anyone can write their own code that skips the filter. Security rules run on Firebase's servers, so they can't be skipped.

Why does a query for all notes fail even if some are mine?

Rules aren't filters. The query must ask only for documents the rules allow, so it has to include where('userId', isEqualTo: uid).
